## 1. Why stockPrincipal > stockIdle with liquidity 0

It is not an unbooked loss. The stock side's claim is partly backed by USDG. This is how the V2 vault
(0x17f0cf26, `PeridotV2-Robinhood/remediation/src/RobinhoodBoostedVaultV2.sol`) and the linked
`SettlementLib` (`src/libraries/SettlementLib.sol`) are designed to behave.

In the pUSDG sync (0x81447d27, block 110130582), `withdrawForSide(USDG, 13,392,022)`:
1. unwound all LP liquidity, then the reserve covered 25,305 USDG;
2. `_settlementSwap` sold 59,382,081,458,909,899 NVDA for 10,339,149 USDG. It updates **idle only**:
   `stockIdle -= used; usdgIdle += output`. The principals stay the same. The code comment says why:
   "Counter principal may be converted here: post-swap loss recognition proportionally adjusts both side
   claims";
3. `_recognizeLoss` then scaled **both** principals by gross/benchmark (PairCheckpoint pnl -0.031621 USD).
   After that, stockPrincipal = 19,752,436,359,047,005 against stockIdle 19,202,066,847,681,856, and
   usdgPrincipal = 13,367,662 against usdgAssets 13,463,785.

The swap input was sized with a `1/(1-1%)` slippage gross-up, and the pool filled better than the floor. So the
USDG side ended up with 96,123 raw more than its claim, and the stock side 550,369,511,365,149 raw NVDA less.
Gross equals benchmark after scaling, so `(stockPrincipal - stockIdle) * P = usdgIdle`. That gives
P = 0.096123 / 0.000550369 = $174.65, the oracle price inside the sync. The loss was booked in full at that
price. What remains is a cross-asset position: NVDA suppliers are owed 0.00055 NVDA, and USDG backs it. Since
then NVDA has risen to $178.73, so the claim is now about $0.0022 under-backed. The next stale-checkpoint path
will book that (see s4/s5 below).

pNVDA's `getCash` counts `withdrawableAssets` = min(idle, principal) = stockIdle. That holds only while the
oracle/removal guard passes: the claims are not natively covered, so the oracle-free idle path is closed. The
exchange rate counts `accountedAssets` = stockPrincipal. The difference is the gap.

## 2. The 0.096123 USDG idle

It belongs to the **stock side (pNVDA suppliers)**. It is the value backing for their 0.00055 NVDA native
deficit. pUSDG cannot withdraw it: usdgPrincipal is 0, so `withdrawForSide(USDG, x>0)` reverts
`InsufficientPrincipal`. It counts in `gross` for every loss recognition. It turns back into NVDA only through
a settlement swap. That swap runs when the stock side withdraws more than stockIdle, **and swaps are unpaused**.
While flags are 110 it stays idle. Any USDG left over after the stock claim is fully paid becomes a "gain" at
the next checkpoint. With native claims covered, `_checkpointPair` adds usdgIdle - usdgPrincipal to
usdgPrincipal, so pUSDG gets the leftover.

## 3. Remedy

**DO NOT run `pNVDA.syncVault` while flags are 110.** The mainnet eth_call and s1 below show what it does. It
spends the NVDA loss reserve: 0.000275 NVDA on the first call and the rest, 0.0000653, on the second, about
$0.061 in total. The gap still ends at 0.00021 NVDA, and the 0.096 USDG stays stranded, because only a settlement
swap can convert it.

**Exact remedy:** reopen swaps through the timelock with `setPairPause(pair, true, false, false)` (flags 100,
allocation stays paused). Then the Ledger, as pNVDA `vaultOperator`, calls `pNVDA.syncVault(type(uint256).max)`
with gas limit 3,000,000. Then the Ledger, as guardian, calls `setPairPause(pair, true, true, false)` (flags 110).
Optionally the Ledger then calls `checkpoint(pair, deadline)` as keeper, so the leftover dust is assigned.
- Roles: `syncVault` is `onlyVaultOperator`, the Ledger. Reopening swaps needs CONFIG_ROLE, the timelock: the
  Ledger schedules, waits 1 h, then executes. The guardian cannot unpause (`GuardianCannotUnpause`). Supplier
  `redeem` calls are permissionless and reach the same `withdrawForSide`, but they only pull what the redeem
  needs.
- This is the same pattern as today's session (schedule, execute, sync, close), with pNVDA in place of pUSDG.
  It needs NVDA market hours: the removal guard and settlement swap revalidate the oracle and pool. It does
  not touch PR 22.

**NVDA suppliers' realised loss:**
- At $178.73, with the remedy above, the booked loss is about 1.26e13 raw NVDA (~$0.0022). It is `loss =
  0.00055037 - 0.096123/P` NVDA, so it is positive only if NVDA is above $174.65 at the sync or checkpoint.
- The surplus the reserve paid in comes back at the follow-up checkpoint and more than offsets it. In s4 the net
  is +2.6e12 NVDA to pNVDA, and pUSDG gets a $0.046 windfall.
- Without reopening swaps, the gap can be cut only to about 0.00021 NVDA (~$0.0375), and that uses up the NVDA
  loss reserve.
- If nothing is done, the gap stays. Whichever suppliers redeem last bear it: redeems succeed only up to stockIdle
  plus local cash, and they do so only while the guard passes. Off-hours withdrawable drops to 0, because claims
  are not natively covered.

**Operator decision: reserve funds land on pUSDG.**
- Reserve cover always runs first and pays up to 50 % of the native deficit value, even though USDG already backs
  the deficit. In s4 the reserve pays 0.000275 NVDA ($0.049). About $0.046 of that ends up as USDG credited to
  pUSDG at the follow-up checkpoint.
- Option (a): accept this. It is a ~$0.046 transfer from the reserve to pUSDG suppliers.
- Option (b): add `lossReserve.configurePair(pair, {...same, maxCoverageBps: 0})` to the same timelock batch.
  The timelock holds reserve CONFIG_ROLE (`hasRole` true; the Ledger has false) and DEFAULT_ADMIN_ROLE. Restore
  5000 afterwards in a second timelock operation. With 0, `cover` returns 0 without reverting, so the swap
  converts the whole 0.096 USDG.
- Do NOT pause the reserve instead. `cover` reverts `ReservePaused`, so the whole withdrawal fails
  (`VaultWithdrawalFailed`).
- Option (b) was not simulated.

**Other caveats:**
- Anvil does not move the feed. NVDA feed 0x379E latestRoundData: answer 178.52828064, updatedAt 1794236342.
  That update came after the sync at 1794234882, so the move from $174.65 is real.
- Live numbers scale with NVDA's price at execution.

**Runbook lesson:** the residual is structural. `_settlementSwap` moves idle only, and `_recognizeLoss` scales
both principals. So a full exit by one side leaves the other side backed by value in the wrong asset.
- A future full-unwind session should sync **both** pTokens while swaps are still open, before
  `setPairPause(true,true,false)`.
- `recovery_session.sh` targets pUSDG, and its GO rule is `returned+loss == usdgPrincipal`. A pNVDA variant
  would need `== stockPrincipal`, with loss at most a few e13 raw. Flagged only, not built.
